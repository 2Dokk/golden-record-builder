# golden-record-builder — 이종 시스템 거래처 마스터 데이터 통합기

> **토이 프로젝트 / 가상 데이터**입니다. 회사명·사업자번호·연락처는 모두 임의로 만든 값이며, 불일치는 검증 목적으로 의도적으로 심었습니다.

같은 거래처가 **영업시스템(CSV)** 과 **회계시스템(JSON)** 에 서로 다른 형식·값으로 기록돼 있을 때,
이를 하나의 신뢰할 수 있는 기준 레코드(**golden record**)로 합치는 MDM(Master Data Management) 파이프라인입니다.

```
[A 영업 CSV] ─┐                                                   ┌─ golden_records (SQLite, UPSERT)
              ├─ ① 스키마 매핑·정규화 ─ ② 매칭 ─ ③ 충돌 해결 ─ ④ 검증 ─┼─ conflicts (수동 검토 큐)
[B 회계 JSON]─┘   (설정 파일 기반)      (사업자번호)  (필드 규칙)   (건수 대사) └─ run_log / rejected.csv
```

## 실행

외부 라이브러리 없이 Python 3.11+ 표준 라이브러리만 사용합니다 (테스트에만 pytest).

```bash
python scripts/make_sample_data.py   # 가상 데이터 생성 (결정적 — 항상 같은 파일)
python -m mdm                        # 통합 실행 → output/ 에 결과
python -m pytest                     # 테스트
```

## 입력 데이터

| | 시스템 A (영업, CSV) | 시스템 B (회계, JSON) |
|---|---|---|
| 회사명 | `회사명` | `거래처명` |
| 사업자번호 | `사업자등록번호` — `000-00-00000` | `사업자번호` — 하이픈 없이 10자리 |
| 고유 필드 | `담당자` | `주소` |
| 전화 | `전화번호` | `대표전화` |
| 기준일 | `최종수정일` — `YYYY-MM-DD` | `등록일` — `YYYY.MM.DD` (일부 `YYYY/M/D`) |

양쪽 모두에 있는 거래처 10곳에 심어 둔 시나리오:

| 시나리오 | 기대 처리 |
|---|---|
| 완전 일치 (2곳, 그중 1곳은 A측 사업자번호 하이픈 누락 입력) | 매칭, 충돌 없음 |
| 회사명 표기만 다름 — `(주)한빛정밀` / `한빛정밀 주식회사` 등 3곳 | 비교 규칙으로 흡수, 충돌 아님 |
| 전화번호 하이픈 유무만 다름 | 추출 단계 정규화로 흡수 |
| 전화번호 불일치, A 또는 B가 최신 (3곳) | 기준일 최신값 자동 채택 |
| 전화번호 불일치 + 양쪽 기준일 동일 | 최신 판단 불가 → 수동 검토 |
| 회사명 실제 불일치 — `대양기공` / `대양테크` | 상호는 자동 덮어쓰기 금지 → 수동 검토 |

그 밖에 데이터 품질 이슈: 검증번호가 틀린 사업자번호 1건(A), 자릿수 부족 1건(B), A 내부 중복 입력 1건, 전화번호 누락 1건, 다른 날짜 형식 1건.

## 처리 단계

1. **스키마 매핑·정규화** — [`config/sources.toml`](config/sources.toml)의 컬럼 매핑으로 공통 스키마(`biz_no, company_name, contact_person, phone, address, as_of`)로 변환. 사업자번호는 숫자 10자리로 통일 후 **검증번호(체크섬) 검사**, 날짜 4가지 형식 → ISO, 전화번호 → `000-0000-0000`. 규칙 위반 행은 버리지 않고 `rejected.csv`에 사유와 함께 격리.
2. **소스 내 중복 제거** — 한 시스템 안에 같은 사업자번호가 여러 번 있으면 기준일 최신 행만 남김.
3. **엔티티 매칭** — 정규화된 사업자번호를 매칭 키로 그룹핑.
4. **충돌 탐지·해결** — 필드별 규칙(설정 파일):
   - `compare`: 같은 값으로 볼 기준. 회사명은 `(주)/㈜/주식회사`·공백을 제거한 키로 비교
   - `on_conflict = latest`: 기준일이 더 최근인 값 채택. **기준일이 같으면 수동 검토**로 넘김
   - `on_conflict = manual_review`: 회사명처럼 잘못 덮어쓰면 위험한 필드는 항상 사람 확인
   - 수동 검토 대상도 잠정값은 채워 두고 `status = NEEDS_REVIEW`로 표시, 필드별 출처(`lineage`)를 기록
5. **검증(건수 대사)** — 아래 항목이 하나라도 어긋나면 **적재하지 않고 중단**
   - 입력 행 = 유효 + 거부 + 소스 내 중복
   - 골든 레코드 수 = 고유 사업자번호 수
   - 골든 레코드 수 = 유효 − (매칭으로 합쳐진 레코드 − 매칭 그룹 수)
   - 충돌 = 자동 해결 + 수동 검토
   - 골든 레코드에 필수값(사업자번호·회사명) 누락 없음
6. **적재(멱등)** — SQLite에 사업자번호 PK로 UPSERT. 레코드 내용 해시를 비교해 **변경된 행만 갱신**하고, 한 트랜잭션으로 처리해 실패 시 전부 롤백. 실행마다 `run_log`에 입력 파일 해시와 통계를 남김.

## 한계

- **가상 데이터 38행** 규모의 검증입니다. 대용량 처리·성능은 다루지 않았습니다.
- 매칭 키가 사업자번호 하나뿐이라, 사업자번호가 없거나 잘못 입력된 레코드는 매칭하지 않고 거부합니다. 실무에서는 회사명·주소 유사도 기반의 보조 매칭(퍼지 매칭)이 필요합니다.
- 회계시스템에는 수정일이 없어 `등록일`을 기준일로 썼습니다. 등록 후 갱신된 값이 있어도 오래된 값으로 판단될 수 있는 한계가 있습니다.
- 수동 검토 결과를 다시 반영하는 흐름(검토 결정 테이블)은 구현하지 않았습니다.
- 입력에서 사라진 거래처는 DB에서 삭제하지 않습니다(soft-delete 정책 미구현).
