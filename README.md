# golden-record-builder

영업 시스템과 회계 시스템에 따로 저장된 거래처 데이터를 사업자번호로 묶어 하나로 합치는 토이 프로젝트입니다.

데이터는 모두 직접 만든 가상 데이터입니다. 회사명, 사업자번호, 연락처 모두 실제와 관계없습니다.

## 만들게 된 이유

여러 시스템에 흩어진 데이터를 하나로 모으는 일이 실제로 어떤 문제를 겪는지 직접 해보고 싶었습니다.

같은 거래처라도 시스템마다 기록 방식이 다릅니다. 영업 쪽에서는 `(주)한빛정밀`, 사업자번호 `601-81-06733`으로 적고, 회계 쪽에서는 `한빛정밀 주식회사`, `6018106733`으로 적는 식입니다. 사람이 보면 같은 회사인데 프로그램은 서로 다른 회사로 봅니다. 이렇게 되면 거래처가 모두 몇 곳인지조차 정확히 셀 수 없습니다.

그래서 두 시스템의 데이터를 일부러 서로 다르게 만들고, 이걸 하나의 기준 데이터(골든 레코드)로 합치는 과정을 구현했습니다.

## 데이터 구성

영업 시스템은 CSV, 회계 시스템은 JSON으로 만들었습니다.

```
영업 시스템 (CSV)   회사명, 사업자등록번호(000-00-00000), 담당자, 전화번호, 최종수정일(2025-03-10)
회계 시스템 (JSON)  거래처명, 사업자번호(하이픈 없음), 주소, 대표전화, 등록일(2025.03.10)
```

두 시스템에 함께 있는 거래처 10곳에는 실제로 생길 법한 차이를 넣었습니다.

- 회사명 표기만 다른 경우 (`㈜동아밸브`, `주식회사 동아밸브`)
- 한쪽 전화번호가 갱신되지 않은 경우
- 전화번호가 다른데 두 시스템의 날짜가 같아서 어느 쪽이 최신인지 알 수 없는 경우
- 상호 자체가 다른 경우 (`대양기공`, `대양테크`)

이 밖에 사업자번호 오타, 자릿수가 모자란 번호, 같은 거래처가 두 번 입력된 행, 형식이 다른 날짜도 섞어 두었습니다.

## 처리 과정

### 1. 형식 맞추기

시스템마다 다른 컬럼 이름을 공통 이름으로 바꿉니다. 어떤 컬럼이 어디에 대응하는지는 코드가 아니라 `config/sources.toml`에 적어 두었습니다. 그래서 다른 시스템이 추가되더라도 설정만 추가하면 됩니다.

값도 같은 형식으로 맞춥니다. 사업자번호는 숫자 10자리로, 날짜는 여러 형식을 모두 읽어 하나로, 전화번호는 하이픈 형식으로 통일했습니다.

사업자번호는 마지막 자리가 앞 9자리로 계산되는 검증번호라서, 계산이 맞지 않으면 오타로 보고 따로 빼 둡니다. 버리지 않고 `rejected.csv`에 이유와 함께 남깁니다.

### 2. 같은 거래처 찾기

회사명은 표기가 제각각이라 기준으로 쓰기 어렵습니다. 대신 회사마다 하나뿐인 사업자번호가 같으면 같은 거래처로 봤습니다.

### 3. 값이 다를 때 고르기

이 부분을 가장 오래 고민했습니다.

먼저 정말 다른 값인지 표기만 다른 건지 구분합니다. 회사명은 `(주)`, `㈜`, `주식회사`, 공백을 지우고 비교해서, `(주)한빛정밀`과 `한빛정밀 주식회사`는 같은 값으로 처리했습니다.

정말 다른 값이면 필드마다 다르게 처리했습니다. 전화번호는 날짜가 더 최근인 쪽을 씁니다. 날짜가 같으면 근거가 없으니 자동으로 고르지 않고 검토 대상으로 넘깁니다. 회사명은 잘못 바꾸면 다른 회사 정보와 섞일 수 있어서, 값이 다르면 항상 사람이 확인하도록 했습니다.

검토 대상이라고 해서 비워 두지는 않았습니다. 일단 가장 그럴듯한 값을 넣고 `NEEDS_REVIEW` 표시를 붙였습니다. 각 값이 어느 시스템에서 왔는지도 함께 기록합니다.

### 4. 숫자 확인

저장하기 전에 처리한 건수가 서로 맞는지 확인합니다. 예를 들어 "입력 행 수 = 정상 처리 + 오류로 뺀 것 + 중복으로 뺀 것"이 맞아야 합니다. 하나라도 맞지 않으면 중간에 데이터가 사라졌거나 두 번 들어갔다는 뜻이라, 저장하지 않고 멈추게 했습니다.

### 5. 저장

결과는 SQLite에 저장합니다. 사업자번호를 기본키로 두고 이미 있으면 갱신하도록 해서, 같은 데이터로 여러 번 실행해도 중복이 생기지 않습니다. 내용이 바뀌지 않은 레코드는 아예 건드리지 않아서, 이번 실행에서 실제로 바뀐 건이 몇 개인지도 알 수 있습니다.

## 실행 결과

가상 데이터로 실행한 결과입니다.

```
[추출] A(영업시스템): 입력 20행 → 거부 1, 소스 내 중복 제거 1 → 유효 18
  거부 A#19: 사업자번호 검증번호 불일치
[추출] B(회계시스템): 입력 18행 → 거부 1, 소스 내 중복 제거 0 → 유효 17
  거부 B#18: 사업자번호 자릿수 오류(10자리 아님)
[매칭] 유효 레코드 35건 → 고유 거래처 25곳 (복수 소스 매칭 10곳, 단일 소스 {'A': 8, 'B': 7})
[충돌] 표기 차이만 있는 필드 3건(정규화로 흡수) / 실제 값 충돌 5건 → 자동 해결 3, 수동 검토 2
(검증 5개 항목 모두 PASS, 로그 생략)
[적재] run_id=1 신규 25, 변경 0, 변경없음 0 → DB 골든 레코드 총 25건
```

정리하면 두 시스템의 38행이 25개 거래처로 합쳐졌고, 그중 10곳이 양쪽에 모두 있던 거래처였습니다. 값이 실제로 다른 경우는 5건이었는데, 3건은 날짜 기준으로 자동 처리됐고 2건(상호가 다른 대양기공, 날짜가 같은 미래용접)은 검토 대상으로 남았습니다.

같은 데이터로 한 번 더 실행하면 이렇게 나옵니다.

```
[적재] run_id=2 신규 0, 변경 0, 변경없음 25 → DB 골든 레코드 총 25건
```

## 테스트

pytest로 22개 테스트를 작성했고 모두 통과합니다. 정상적으로 합쳐지는 경우, 최신 값을 고르는 경우, 날짜가 같아 검토로 넘어가는 경우, 어느 쪽에도 매칭되지 않는 신규 거래처, 같은 데이터로 다시 실행하는 경우를 확인합니다.

세 번째 시스템(구매 시스템 CSV)을 설정 파일만 추가해서 붙였을 때 기존 거래처와 제대로 합쳐지는지도 테스트에 넣었습니다.

## 실행 방법

Python 3.11 이상이면 따로 설치할 라이브러리는 없습니다. 테스트에만 pytest가 필요합니다.

```bash
python scripts/make_sample_data.py   # 가상 데이터 생성
python -m mdm                        # 실행, 결과는 output/ 폴더에 생성
python -m pytest                     # 테스트
```

## 아쉬운 점

- 38행짜리 가상 데이터로만 확인했습니다. 데이터가 많아졌을 때의 성능은 확인하지 못했습니다.
- 사업자번호가 없거나 잘못된 데이터는 합치지 못하고 빼 둡니다. 실제로 쓰려면 회사명이나 주소가 비슷한지 보고 후보를 찾아 주는 방식이 더 필요할 것 같습니다.
- 회계 시스템에는 수정일이 없어서 등록일을 기준으로 최신 여부를 판단했습니다. 등록 후에 값이 바뀌었다면 판단이 틀릴 수 있습니다.
- 검토 대상으로 넘긴 건을 사람이 확인한 뒤 다시 반영하는 기능은 아직 만들지 않았습니다.
